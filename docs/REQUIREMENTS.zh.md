## 〇、设计总原则(优先级高于一切具体需求)

**使用者是社区超市的老板和店员,文化程度普遍不高、对软件耐心极低。任何功能在"有用"和"简单"冲突时,选简单;每个界面、每个流程都要过一道关:"一个不太会用手机的五十岁店员,不用人教能不能用起来?"过不了这道关的功能宁可不做。**

---

## 一、背景与痛点

目标客户是顾客语言背景很杂的社区超市(华人超市、韩国超市、拉美超市等)。"某某东西在哪儿"是店员每天被问得最多的问题——顾客可能用中文或英文问,可能拼错品牌名,甚至只能描述外观("做寿司的那种黑色的纸")。

商品位置知识只存在于老员工脑子里:新员工答不上来,老员工不停被打断。而且**没有任何一家店有时间和意愿人工录入、维护商品数据库**——所有要求录 SKU、贴标、建库的方案在这类店注定失败,这是产品设计的底线约束。

---

## 二、产品核心理念

一个**"自己会长大的店面记忆"**:

- 店员平时路过货架顺手拍几张照片,系统自动识别商品、自动生成多种叫法(中英文、拼音、常见拼写错误),把"什么商品在哪个货架"记下来;
- 同一商品被拍到的次数越多,记忆越可信;
- 之后顾客用任何方式来搜,都能得到"在几号货架"的回答加地图标注。

**拍得越多,搜得越准;全程零人工录入。**

## 四、产品本体

### 4.1 顾客端(公开,免登录免安装)

**入口与店铺网址**

- 官网主站在 `www.whataisle.com`,每家店开通时选定一个店铺标识(如 `xxyyzz`),该店顾客端就是 **`xxyyzz.whataisle.com`**。
- 店铺标识规则:只允许字母、数字、连字符;全平台唯一;保留字(`www` / `admin` / `api` / `help` / `app` 等)不可注册;开通时实时校验可用性;要有防冒用机制(不能注册别家知名超市的名字碰瓷,发现可由平台方仲裁收回)。
- **子域名一经选定终身不可改**:选择页用一句话讲清后果("这是顾客访问你店铺的永久网址,会印在海报上,想好再定"),并展示预览(`xxyyzz.whataisle.com`)让老板二次确认。店铺展示名随时可改,不影响网址;店铺转手时网址跟店走。
- 系统一键生成含二维码和明文网址的**店内海报、收银台立牌、货架贴**打印文件——"顾客怎么知道能扫码找货"是产品的事,不是老板的事。网址要能读出口、顾客记得住。
- 访问不存在或已注销的子域名,显示统一的"没有找到这家店"页面,附一句引导到主站——每个失效链接也是一次获客曝光。

**搜索输入**

- **三种并列的输入方式**:打字(中英文、拼错、纯描述都行)、**按住说话**的语音输入、**拍照识别**商品。
- 语音和拍照都有"确认识别结果"的中间步骤:先显示"我听到的 / 认出的是 XX",用户确认或重试后再搜,容错口音和识别偏差;嘈杂卖场里语音拿不准时给几个候选让顾客点选,而不是单一结果反复失败。

**搜索结果页的标准形态**(结构固定,自上而下)

1. **顶部**:返回入口、页面标题、右上角 EN/中 语言切换;下方回显顾客的原始查询(如 ""韩式辣酱"")。
2. **思考过程折叠条**:搜索中实时展开显示系统在做什么(理解问题 → 查店面记忆 → 选答案);出结果后自动折叠成一行"HOW IT SEARCHED · 3 STEPS"(标注步骤数),想看的可点开——答案才是重点,过程不能喧宾夺主。
3. **答案横幅**:一句人话、带底色突出,随界面语言单语显示,例:"Found a few possibilities — most likely Wang Korea Gochujang on shelf B4."。四种语气:
   - 自信命中("应该是 B4 货架的 XX")
   - 多个候选("找到几个可能的,最可能是……")
   - 品类指引(没有精确结果时,"这类通常在 B4 附近")
   - 明确的没找到
4. **候选商品列表**:一个问题可能命中多个相似商品(顾客问"韩式辣酱",店里有五种辣酱膏),**按可能性排序全部列出**并标注数量("5 POSSIBLE ITEMS")。每张卡片含:货架实拍缩略图、商品名、带定位图标的**货架号徽章**(如 B4)、被拍到次数("seen 1×")。缩略图必须是这家店货架上的实拍裁剪——顾客拿着手机对照包装找货,网图没有用。
5. **"WHERE TO FIND IT" 平面图**:店内平面图上**目标货架标红**,周边货架(如 B5、C3)正常显示供定位参照;平面图组件支持"主货架 + 左右侧面位(L/R)"的结构;候选商品分布在多个货架时,可点选切换标红。

**其他**

- 结果页提供免登录的**"按图找了,不在这"一键反馈**(详见第八节)。
- 没搜到时引导换个说法,并把这次"没找到"记入洞察。

### 4.2 员工端(店内使用)

- 店员输入**店级 4–6 位 PIN** 即可进入,不需要注册账号(店员是低技术意愿人群,任何多余步骤都会杀死使用意愿);PIN 由老板设置、可随时改。
- **扫货架录入**是核心流程:
  1. 选货架(平面图点选,或货架编号列表);
  2. 现场拍照,或从相册**一次多选**批量上传;
  3. 每张照片独立处理状态(待处理 / 识别中 / 完成 / 失败),单张失败不阻塞整批;
  4. 识别结果**跨照片合并去重**,可删掉误识别项;
  5. 一键保存,实时进度展示。
- 保存时系统自动完成两件事:
  - 为新商品生成**固定组合的多语言别名**(英文、中文、拼音/罗马音、常见拼写错误)——不做任何语言配置项,以后有非中英客群的店再扩展;
  - 把这次拍摄记为一次**位置印证**,支撑"seen N×"的可信度展示。
- **货架管理**:按货架浏览商品、编辑(名称/别名/品类/货架)、删除、手动新增;整架清空等破坏性操作仅老板账号可做,且二次确认(显示将影响多少商品)。
- **测试搜索**:店员录完当场自查"顾客现在能不能搜到",演练流量不计入统计。

### 4.3 老板看的数据洞察

- 热搜商品排行、命中率;**"顾客找不到的商品"**分两个清单:
  - 店里真没有 → 呈现为进货参考;
  - 店里疑似有但没拍 → **一键生成补拍提醒**,店员补拍保存后自动销账。
- **自动周报**发到老板邮箱:搜索量、热搜、找不到的商品、店面记忆涨了多少、本周修正了几条错误——老板不会主动登后台,周报是持续证明产品价值、防流失的关键触点。
- 老板端只显示用量(拍了多少张、顾客搜了多少次),**不显示任何成本金额和内部技术指标**。

## 五、租户与账号

- 每家店是**完全隔离的租户**:商品记忆、照片、平面图、日志、统计互不可见。**"顾客搜出别家店的货架号"是最致命事故,写进验收标准。**
- 账号只有两层,**不做角色系统**:
  - **老板账号**:邮箱/手机号正规注册登录,可自助找回;管店铺配置、货架管理、数据洞察、数据导出;
  - **员工 PIN 入口**:只能扫货架和测试搜索。
- 破坏性和敏感操作(整架清空、批量删除、改配置、导出数据)必须老板账号执行并二次确认。

## 六、开店流程与平面图(不做编辑器,传视频、我们制图)

- **平面图编辑器第一版不做**。流程:老板开通后,产品引导他**拍一段店内视频**(绕店走一圈,拍清货架布局和过道牌,给一屏拍摄指引)并上传;**我们收到视频后人工制作该店的平面图**,发布到他店里;老板核对"图上编号和店内过道牌一致"后确认,不一致可留言打回。制图时效**不做对外承诺**,内部按队列管理。
- 产品要支撑这条链路:
  - **大视频上传**:手机拍的大文件传得上来——支持多段视频、上传进度可见、断网续传、传完有明确的"我们已收到"确认;
  - **平台方的制图工单**:视频到达通知我、后台可下载、内部制图工具(不用傻瓜化,自己人用)把平面图和货架编号配置到该店名下、一键发布并通知老板;
  - 确认后配套的**货架号标签**可打印(图上编号必须和店内过道牌一致,这是"照图找得到"的前提)。
- **等图期间不空等**:平面图做好之前,老板可以先按"货架编号列表"开始拍货架建记忆,顾客端先用"3 号货架"文字指引;图发布后自动关联既有货架,已录入数据一条不丢。**制图绝不能挡住第一次拍摄——注册当天就要能拍第一个货架并在顾客端搜到。**
- **后期调架**:老板在产品里发起"布局更新"请求(重传视频或文字说明),我们改图重新发布;货架的移动、合并、拆分,**商品记忆必须跟着走、不丢数据**。

## 七、平台方(卖家自己)的运营后台

- **租户总控台**:每家店一行——状态、商品数、近 7 天顾客搜索量、最近扫货时间、本月 AI 成本、健康度;自动生成流失预警清单("7 天零搜索""30 天零更新")并附建议动作。低客单价订阅丢一家很难补一家,留存必须靠主动运营,不能等店家投诉才知道出事。
- **制图任务队列**:待制图 / 制图中 / 待老板确认 / 已发布,集中排期,超时标红——制图是对每个新客户的第一个交付,不能靠记性。
- **按店成本核算**只在平台后台;异常用量(疑似爬虫、误操作、单店暴增)触发**告警 + 人工介入**,不自动断服。
- **模拟进店**能力(只读 / 代操作两档,全程留痕)——远程支持"我这边显示不出来"类问题的唯一高效手段;内置**工单系统**(店家一键报障,自动附带店铺标识和上下文);主动公告推送;中英文自助帮助中心。
- 店家端**不提供任何暴露内部数据结构的调试类界面**;跨店数据查看、排查工具只存在于平台后台。店家端保留说人话的"数据健康页"(商品总数、货架覆盖、最近录入、异常项)。
- **可用性按店家的营业时间定义**,不按平台的钟表:维护窗口避开营业时段;**任何一家店的操作峰值(建档日批量传照片、上传店内视频)不得拖慢别家店的顾客搜索**,作为硬性验收标准;AI 服务不可用时,顾客端自动降级为基于已有别名的文字匹配并友好提示,绝不白屏;发版不得中断营业中店铺的搜索。
- **数据所有权与注销**:白纸黑字"店面记忆归店家所有",老板随时自助导出(商品—别名—货架对照表、原始照片、平面图),不限次不收费;**注销即删除、不设保留期**——因此注销流程必须强引导"先导出数据"、明示"删除后无法恢复"并双重确认,删除完成后发确认函。

## 八、保持记忆正确(不做自动过期,靠简单规则 + 人工闭环)

- 商品可以有**多个在售位置**(常规货架和促销堆头都拍了就都展示),不做自动仲裁和有效期机制;位置不对了,店员在货架管理里手动删掉即可。
- **纠错闭环是质量兜底,必须做**:
  - 顾客端"按图找了,不在这"一键反馈 → 同一商品被多人反馈后,该答案自动降为"建议确认"语气,并生成店员核查提醒;
  - 店员在搜索结果页**就地纠错**(直接改货架 / 删误识别),不用绕进管理页;
  - 反馈只能降语气、不能直接改数据——公开入口必然被恶意点击,任何数据变更必须由店员确认;
  - 周报回显"本周修正了 N 条"——老板必须看得到系统在变准。
- **存量导入(可选,二期也行)**:支持上传 POS 导出的商品清单(CSV),预生成别名、状态"未定位"(暂不参与顾客搜索),扫货时照片识别结果自动与清单匹配合并——缩短建档时间。

## 九、语言与实体环境

- **界面只做两种语言:英文和中文**,一键切换,不做店级语言配置。销售材料、帮助中心、条款也只做英中两套。
  **【2026-07-28 加注】官网默认语言跟随访客的浏览器/手机系统语言**(中文系统自动进入 `/zh`),
  手动切换后用 `NEXT_LOCALE` cookie 记住一年;搜索引擎抓取不受影响(裸域名仍返回英文页)。
- **店家品牌优先**:顾客端页头展示店名和店家 logo(店铺档案:店名、logo、营业时间、公告,老板随时可编辑),页脚保留统一的平台标识——老板买的是"我自己店的找货助手",顾客界面必须看起来是店家自己的服务。
- **实体卖场当一等公民**:
  - 店内弱网/断网时照片本地暂存、恢复自动续传、上传队列可见、锁屏切后台不丢任务;
  - 所有错误文案友好、说人话,严禁向顾客暴露技术性报错;
  - 手机竖屏是第一形态,"扫码即用、免安装"写进验收标准;店员端引导添加到手机主屏;
  - 相机/麦克风权限被拒后不许死路,给替代路径(拍照被拒 → 引导打字)并说明如何重新开启。
- **店员培训材料**:一页纸操作卡(贴休息室)+ 2–3 分钟操作短视频,英中两版——超市店员流动性高,店家必须能自己训练新人,否则产品会因人员更替而荒废。

## 十、合规与内容安全

- 注册流程有条款勾选并记录版本,条款更新需重新确认。
- **免责条款**写明:"本服务仅提供商品位置指引,仅供参考,不构成任何商品建议"——位置准确率不做任何量化宣传。
- 照片与数据:
  - 员工拍的货架照片检出人脸自动打码;顾客端商品缩略图只裁商品区域(顾客端公开可访问,是照片泄露最大出口);
  - **店内视频留存**,仅平台方制图和存档使用,不对外、不出现在任何店家或顾客界面;
  - 顾客拍照搜索的照片和语音是顾客的个人数据,识别完成后短期内自动删除,入口一句话告知("照片仅用于识别商品,不会保存");老板只能看文字化的查询,不能回放顾客原声。
- **与 AI 供应商的条款逐条书面确认:允许本产品的商用转售形态、店家照片与数据不用于模型训练**——上游条款不允许商用,整个生意的地基就是违约的。这是第一优先级的核查项。
- **内容安全**:每家店的顾客端都是无登录的公开 AI 入口,必然有人来玩坏它——套话术、辱骂、无关闲聊一律礼貌回"我只会帮你找商品",不执行、不计入热搜统计;顾客端不提供任何可遍历全店商品的形态,配合速率护栏,防止多语言别名库被竞品整库爬走——那是全平台最值钱的数据资产。

## 十一、已拍板的原则(给产品经理对齐用)

1. 一切从简,使用者文化程度不高,复杂功能宁可不做。
2. 销售地区不限定;语言只做英文 + 中文。
3. 一个账号一家店,不做连锁、不做跨店数据共享。
4. 每店子域名 `xxyyzz.whataisle.com`,一经选定不可改。
5. 平面图不做编辑器:客户传店内视频,我们人工制图;制图时效不做对外承诺。
6. 店内视频留存(仅平台内部使用)。
7. 注销即删除数据,不设保留期(注销前强引导导出 + 双重确认)。
8. 不做记忆自动过期,记忆质量靠顾客反馈 + 店员就地纠错兜底。
9. 位置准确率不写进任何宣传,免责条款覆盖。
10. 定价、计费、试用机制本文不涉及,后续单独定。

## 十二、部署约束

整个服务(店铺网页、后台、AI 识别与搜索能力)**部署在 Google Cloud 上**,这是定死的技术边界,选型都在其生态内解决。

- 域名 `www.whataisle.com`;店铺子域名(`*.whataisle.com`)的**泛解析和证书**要在部署架构里一并支持。
- 云上要设**预算上限和费用告警**——"不限搜索"的承诺下,云费用失控是平台方最大的经营风险,费用监控是上线的前置条件,不是事后补的。
